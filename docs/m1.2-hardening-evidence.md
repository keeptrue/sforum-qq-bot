## 1 探针工具（preview / test_push / status）没有 actor 闸

### 1.1 现象

三个工具的行为都与「谁在调用」无关：`testPushHandler` 会真的往白名单第一个群发一条消息，`statusHandler` 会打印完整群 ID，`previewHandler` 只渲染。三个 handler 都不读调用者身份，插件里也没有任何权限常量或 actor 判断（全仓库 `grep -n "Actor\|Permission" backend/*_test.go` 零命中，`backend/*.go` 亦无）。

### 1.2 代码位置（插件侧）

| 位置 | 内容 |
| --- | --- |
| `plugins/sforum.qq-bot/backend/tool.go:82-103` | 三条 `AIToolDefinition` 注册，`Execute` 直指三个 handler |
| `plugins/sforum.qq-bot/backend/tool.go:108-164` | `testPushHandler`：只用 `call.Arguments`（:110），真发消息（:157） |
| `plugins/sforum.qq-bot/backend/tool.go:168-171` | `statusHandler`：签名 `(_ context.Context, _ *pluginv2.AIToolCall)`，连 call 都不看 |
| `plugins/sforum.qq-bot/backend/tool.go:178-229` | `previewHandler`：只读 `call.Arguments` |
| `plugins/sforum.qq-bot/backend/tool.go:287-295` | 状态输出打印**完整**群 ID（`claim.GroupID`，未经 `maskGroupID`） |
| `plugins/sforum.qq-bot/backend/routes.go:59-76` | 路由分发，同样不看 actor |
| `plugins/sforum.qq-bot/sforum.extension.json` `routes[].guard/permission` | 五条路由均为 `guard: core.guard.permission`、`permission: sforum.qq-bot.manage`、`access: permission`、`fallback: closed` |
| `plugins/sforum.qq-bot/sforum.extension.json` `permissionDefinitions` | 仅 `sforum.qq-bot.manage`，`assignmentPolicy: host` |
| `plugins/sforum.qq-bot/sforum.extension.json` `aiTools[].context` | 三条工具**都未声明** `context`（默认只给 locale，而 locale 也只在声明后才填） |

### 1.3 宿主到底按什么放行：三条链路，三种口径

**链路 A：组件模式的插件路由**（设置页组件 `frontend/admin/src/api.ts` → `/extensions/sforum.qq-bot/*`）

- 宿主先跑守卫：`app/Support/Routes/core_guard_authorizer.go:206-207` → `requireAnyCoreGuardPermission`（:341-354），要求 `Authenticated && ActorID>0`，且 `Permissions["*"]` 或 `Permissions["sforum.qq-bot.manage"]` 为真；否则 403，插件根本收不到请求。
- 通过后宿主把 actor 送进插件：`app/Http/route_dispatcher_v2.go:62-75`（`Actor: NewProtocolV2RouteActor(ActorID, Authenticated, Permissions)`）→ `app/Support/Extensions/protocol_v2_actor_delegation.go:62-70`（写 `protocolv2.Actor{UserId, PermissionKeys}`）。所以**只有路由链路插件拿得到 actor**。

**链路 B：schema 回退模式的设置页探测**（`POST /admin/extensions/:id/settings/actions/:actionId`，`app/Http/Controllers/Extensions/routes.go:85`）

- `app/Models/Extensions/settings_actions.go:17-94`：先 `canManageExtensionSettings`（:31-33）——即 `extension.plugin.manage` 或 `extension.manage`（`app/Models/Extensions/service.go:574-576`；主题/mail/identity 三种额外放行对本插件不适用）；再按 `kind` 分流，`ai_tool_probe` 走 :64-68。
- `app/Support/Extensions/settings_actions.go:28-47` 起一个短命 runtime，`probeSettingsActionAITool`（:72-107）只把 `request.Values`（草稿设置）序列化成 `arguments`（:88-91）调 `InvokeVersionedAITool`（:92-99）。**整条链路没有任何 actor 参数**。
- 结论：链路 B 的闸是 `extension.plugin.manage`，与链路 A 的 `sforum.qq-bot.manage` 是**两个不同的权限键**，覆盖同一批副作用（发真消息、读群 ID）。

**链路 C：模型调用**（AI 补全循环里的工具）

- 登记不等于暴露：`bootstrap/ai_plugin_tools.go:105-124` 把「已启用插件声明的工具」登记进宿主 `ToolRegistry`（停用插件跳过，:52-59），注释明说「Core 用途的白名单不含插件工具，因此登记不会改变任何现有对话的行为」。
- 模型能看到什么由用途白名单决定：`app/Support/AI/purpose_resolver.go:57-87`（用途声明 → 站点覆盖）→ `RunInput.ToolNames` → `app/Support/AI/tool_loop.go:275-296`（`registry.Lookup` 与 `toolAllowed` 双重闸）。
- 白名单条目只校验工具名**语法**（`app/Support/AI/validation.go:39-58`：长度、`ValidToolName`、去重），不校验「这个工具是不是管理员工具」。运营者在站点 AI 设置里写 `qq-bot-test-push` 就会保存成功。
- AI 工具派发**按设计不带 actor**：`app/Support/Extensions/protocol_v2_ai_tool.go:94-105` 的 payload 只有 `name/arguments`，可选 `locale/topicId/viewerUserId`；`app/Support/Extensions/protocol_v2_client.go:772-789` 的 `requestContext` 不挂 Actor；SDK 把这钉成不变量——`sdk/plugin/v2/ai_tools_test.go:27-28`：`if call.Context.GetActor() != nil { t.Fatal("tool dispatch must not carry actor authority") }`。
- 补充：`aiTools[].context` 只允许 `locale`/`topic`/`viewer`（`app/Support/ExtensionManifest/v3_ai_tools.go:49-57`），`viewer` 是**提问的浏览者**，不是操作管理员——即使声明了也对「闸门」无意义。

### 1.4 真实可利用面与误判风险

1. **当前默认状态是安全的**：默认用途白名单不含插件工具，模型看不到 `qq-bot-test-push`。风险是**配置漂移**——运营者在 AI 设置里加一个合法工具名，就从「模型调不到」变成「模型能发真消息，且无任何 actor 闸」。
2. **插件侧对链路 B/C 无从判断**：三个 handler 拿到的 `AIToolCall` 在两条链路上形状完全一致（只有 `Arguments`），`Context.Actor` 恒为 nil。想「自己加 actor 校验」在结构上做不到。
3. **超管与普通管理员的实际差别（这是本条最容易被误判的地方）**：
   - 超管：`Permissions["*"]`，链路 A 与 B 都过。
   - 默认角色「技术管理」`tech_admin`：持有 `extension.plugin.manage`（`app/Models/Identity/seeds.go:228-243`，权限项在 :234），**不持有** `sforum.qq-bot.manage`。→ 它能走链路 B：在设置页点「发一条测试消息」真的发一条到白名单第一个群，点「推送状态」看到完整群 ID；但它调不动 `/test-push` 路由。
   - 默认角色「站点运营」`operator`：两个键都没有（`seeds.go:192-226`），两条链路都过不去。
   - 若运营者把 `sforum.qq-bot.manage` 授给某角色，该角色拿到链路 A，却不必然有链路 B 的权限。
   → 「谁能发测试消息」取决于他从哪个入口点，这是权限模型的口径分裂，不是插件的 bug。
4. **结论：插件侧不该加这个闸**。链路 A 加校验只是把宿主已判过的同一判定复读一遍，还要自己解释 `*` 语义与权限键（清单改键时静默失效或放大）；链路 B/C 结构上拿不到 actor。要收紧只能改宿主。

### 1.5 最小修法候选

| 候选 | 做法 | 代价 | 副作用 | 判定 |
| --- | --- | --- | --- | --- |
| A（插件侧，可做） | 三个 handler 与五条路由统一从 `request.GetContext().GetActor()` 取 `UserId/PermissionKeys`，要求含 `sforum.qq-bot.manage` 或 `*` | 复制宿主守卫；`*` 语义自实现；清单改键要两处同步（`manifest_contract_test.go` 可钉住） | 无（正常请求宿主已放行过），但**链路 B/C 仍然无闸**，只是让「看起来加了闸」 | **不做**：收益近零，制造第二套权限解释 |
| B（宿主侧，上游建议） | ① 给 `sforum.ai.tool.invoke.request@1` 增 `purpose` 与 actor 事实；或 ② `ai_tool_probe` 要求 super_admin（照 `executable trust` 的口径） | 跨仓库改宿主契约，需宿主版本与迁移 | ② 会让 `tech_admin` 失去「测推送」能力，运营上可能是倒退 | 记录为上游 issue，不在本仓库落 |
| C（本仓库，零代码） | 维持「这三个工具不是给模型用的」的清单文案（现状已写明「模型不应调用它」），并在 M1.2 文档里把「不要把插件工具加进用途白名单」写成运营约束 | 零 | 无 | **推荐现在做**（属纯文档，零摘要影响，见 §5） |

### 1.6 判据

- 文档侧：本条与 §5 的「运营约束」进入 `docs/`，`git status --short plugins/` 仍为空。
- 证据侧（验证「宿主确实按用途白名单放行」而非插件判断）：在站点 AI 设置里把 `qq-bot-test-push` 加入某用途白名单 → 触发一次该用途的回复 → `ai_executions`/`toolTrace` 里出现该工具的成功调用；移出白名单 → 同一调用变成 `ToolFailureNotAllowed`（`tool_loop.go:285-293`）。
- 若将来采纳候选 A：单测构造无 actor 的 `RouteRequest` → 期望 403；有 actor 但缺权限键 → 403；`PermissionKeys` 含 `*` → 200。

## 2 `/bind/poll` 的任务不绑定创建者

### 2.1 现象

`/bind/start` 生成任务后，任务表只存「taskID → 解密密钥」。`/bind/poll` 只按 `taskId` 查表，不看是谁在问。任何拿到 taskID 的调用方都能把扫码完成后的 AppSecret 取走——而且是**先到先得**，原发起者只会看到 `expired`。

### 2.2 代码位置

| 位置 | 内容 |
| --- | --- |
| `backend/routes.go:79-107` | `routeBindStart`：`p.bindStore.Put(task.TaskID, task.Key)`（:101），**未带任何调用者信息** |
| `backend/routes.go:111-145` | `routeBindPoll`：`taskID := routeStringValue(routeBody(request), "taskId")`（:116）→ `p.bindStore.Key(taskID)`（:121）→ `p.bind.PollBindTask(ctx, taskID, key)`（:125）→ `Take(taskID)`（:140）→ 交付 `result.AppID/result.AppSecret`（:143-144） |
| `backend/routes.go:131-142` | 抢输的一方回报 `bindStatusExpired`（:141），**不是错误**，发起者无法察觉被截走 |
| `backend/bindstore.go:22-26` | `bindTaskEntry{key string; createdAt time.Time}`——没有 owner 字段 |
| `backend/bindstore.go:83-96` | `Put(taskID, key string)` |
| `backend/bindstore.go:99-115` | `Key(taskID)`：只按 taskID 读 |
| `backend/bindstore.go:118-134` | `Take(taskID)`：只按 taskID 取走并删除 |
| `backend/bind.go:129-155` | `CreateBindTask`：taskID 由平台下发（`data.task_id`），密钥是本端 CSPRNG 生成 |
| `backend/bind.go:195-205` | `PollBindTask` completed 分支：`decryptBindSecret(key, data.Secret)`（AES-256-GCM，密钥只在本进程内存） |

### 2.3 真实可利用面

- **不是「猜 taskID」**：taskID 由 q.qq.com 下发、10 分钟 TTL（`bindstore.go:13`）、每进程每分钟最多建 5 个（:16）、表上限 64（:19），暴力枚举不现实。
- **是「拿到 taskID 的第二个调用方」**：同站的另一个技术管理员/超管、共享同一浏览器配置的第二个会话、被截图/工单/聊天记录带出去的 taskID、admin 页面上的同源 XSS（CSRF 挡不住同源脚本）。危害是 AppSecret 落到发起者以外的人手里，且发起者只看到 `expired`。
- **能力增量有多大**：拿到 AppSecret 的人本来就能「自己重新走一次绑定」（同一权限即可），所以这不是权限提升，而是**跨账号的凭据截取 + 不可察觉**：可以把别人的机器人凭据绑到自己的控制下（改 AppSecret 后原管理员只看到「推送失败」），或者单纯取走一份长期凭据。
- 现有缓解（保留，不改）：凭据只交付一次（`Take`）、10 分钟过期、启动限流、密钥只存内存不落盘不进日志。

### 2.4 最小修法候选

**候选 A（推荐）：把发起者身份写进任务条目。**

- `bindTaskEntry` 增 `ownerID int64`（`bindstore.go:22-26`）；`Put(taskID, key string, ownerID int64)`；`Key`/`Take` 增 `ownerID int64` 参数，不匹配按「不存在/过期」返回 `false`（复用现有 `expired` 语义，前端零改动）。
- `routes.go:101` 传 `request.GetContext().GetActor().GetUserId()`；`routes.go:121`、`:140` 传同一个值。actor 一定存在：五条路由都是 `core.guard.permission`，宿主 `requireAnyCoreGuardPermission` 已要求 `ActorID>0`（`core_guard_authorizer.go:341-354`），并在 `route_dispatcher_v2.go:71-73` 送到插件。仍保留「actor 为 nil 或 UserId<=0 时拒绝」的兜底分支，避免未来新增无守卫入口时静默放行。
- 代价：`bindstore_test.go` 8 个用例、`routes_test.go` 里 bind 相关 5 个用例需要补 owner 参数（约 30 行机械改动）；`Put` 签名变化会牵动 `routes_test.go:141-421` 的 setup 代码。
- 副作用：同一账号换浏览器/换会话仍可 poll（同 UserId）——这正是期望；换账号不能。插件重启后任务表本来就清空，行为不变。不引入持久状态、不改 schema、不动前端与 dist。

**候选 B（更严）：`/bind/start` 额外返回一次性 handle，`/bind/poll` 必须带 handle。**

- 前端把 handle 与 taskId 一起放在组件内存（`bind-card.ts:61` 附近）。
- 代价：改 `schemas/bind-start-output.json`、`schemas/bind-poll-input.json`、`openapi/routes.yaml`、前端 `api.ts`/`bind-card.ts`、重建 dist；摘要随之变化。
- 收益：连「同账号的另一会话」也挡住。除非确实要防同账号并发，否则不做。

**候选 C（不推荐）**：把交付绑到 `Idempotency-Key`。语义不对——poll 本来就是反复读。

### 2.5 判据

- 新增单测（store 级）：`Put("t", key, 7)` → `Take("t", 8)` 返回 `false` 且条目仍在 → `Key("t", 7)` 仍可读 → `Take("t", 7)` 成功。
- 新增单测（路由级）：以 user 7 调 `/bind/start`，以 user 8 调 `/bind/poll` → `status=expired`、`appId/appSecret` 皆空；再以 user 7 调 → `status=scanned` 且拿到 secret，且 `bindStore.Len()==0`。
- 回归：`TestRouteBindPollDeliversSecretOnce`、`TestRouteBindPollConcurrentDeliveryIsExclusive`、`TestBindStoreOneTimeTake`/`TTL`/`TrimOldest`/`RefundStart` 全过（改成同 owner）。
- 手工冒烟：两个浏览器分别用 `tech_admin` A 与超管 B 登录 → A 出码 → B 用 A 的 taskID poll → `expired`；A 自己 poll → 回填成功。

## 3 preview 空模板回落已保存模板，导致前端 `previewEmpty` 文案不可达

### 3.1 现象

运营者把模板框清空后，预览面板显示的不是「空」，而是**已保存模板**的渲染结果；文案「（模板为空，渲染结果也是空的）」在实际操作里几乎看不到。

### 3.2 代码位置

| 位置 | 内容 |
| --- | --- |
| `frontend/admin/src/template.ts:112-118` | 预览请求体**总是**发送五个键，清空即空串 |
| `frontend/admin/src/template.ts:99-106` | `setText`：`const empty = text === ''` → `body.textContent = empty ? t('template.previewEmpty') : text` |
| `frontend/admin/src/i18n.ts:39`（zh）/ `:115`（en） | `template.previewEmpty` 文案定义 |
| `backend/routes.go:234-259` | `resolvePreviewDraft`：`if template := routeStringValue(values, "template"); template != ""`（:242-244）——**空串等同「没给」**，回落到 `config.MessageTemplate` |
| `backend/routes.go:225-232` | `previewDraft` 的注释：「请求里缺哪一项就回落到已保存配置」——把「空」和「缺」混成一件事的书面依据 |
| `backend/tool.go:197-212` | schema 回退路径的 `previewHandler` 用同一约定（`draft.MessageTemplate != ""`，:197） |
| `backend/config.go:126`、`:136-138` | 已保存模板**不可能为空**：`MESSAGE_TEMPLATE` 为空或全空白时保留 `defaultMessageTemplate`（:31-35） |
| `backend/template.go:64-100` | `Render` 不做整体 trim：模板若只含解析为空的变量（如 `{{signature}}` 且签名为空），结果就是空串 |

### 3.3 判断：该改行为，不是该改文案

- 现在的实际行为是「我清空了，预览还是旧内容」——这是**行为**错，运营者会以为预览卡住或没生效。文案本身没错，只是**几乎不可达**：唯一能触发它的是「渲染结果恰好为空串」（例如已保存模板 `{{signature}}` 且签名为空），而「模板框为空」这条最自然的路径被回落吃掉了。
- 两条路各自影响什么：
  - **改行为（presence-aware）**：区分「键不存在」与「键存在但为空串」。清空模板 → 预览真空 → `previewEmpty` 立刻可达，所见即所得。影响面：`routes.go:242-244` 与 `tool.go:197-199` 两处；`parseDraftArguments` 要能区分「没给」与「给了空串」（返回 `*string` 或 ok 标记）；`TestRoutePreviewFallsBackToSavedConfig`（`routes_test.go:469`）的语义要改成「缺键才回落」；schema 回退路径（host 表单 → probe tool）也会跟着变——表单清空后预览为空而不是保存值，这与组件模式一致，是好事。`maxMessageChars` 的「0 表示沿用默认」是**另一条独立约定**（`routes.go:254-257`），必须保留。
  - **改文案（删 key 或改成「模板为空时沿用已保存模板」）**：零行为变化、改动最小，但把「清空看到旧内容」永久固化；而且改行为后这个字符串是**正确**的，现在删掉等于删掉一个马上要用的文案。
- 结论：**改行为**，文案保留。这属于行为改动（动包内代码 + 改测试），归入同一批打包，不现在动。

### 3.4 最小修法候选

| 候选 | 改动 | 代价 | 副作用 |
| --- | --- | --- | --- |

## 5 加固窗口：为什么必须等 v0.2.0 tag 之后，并与模板预设合并成一次打包

### 5.1 现状

- `git tag --list 'v*'` 为空：**v0.2.0 还没打**。
- 四点里 2、3、4 与「模板预设」全部落在**包内**文件（`backend/*.go`、`manifest/settings.json`、`frontend/admin/src/*`、`frontend/admin/dist/*`），1 的落地形式是纯文档。

### 5.2 为什么每批只能打一次包（NOTES §5 的固定成本）

`NOTES.md:57-68`（§5）钉住两件事：① 宿主按 `backend.digest` 与包内可执行文件实际摘要比对，对不上就拒绝启用；② **改了包内任何文件都要重跑 `prepare-package.sh`**，摘要变了旧信任授权即失效，后台显示「升级」，必须重走「授权当前精确制品 → 确认并升级」；同版本号只改内容时，卡片上的「重启」**不会**切换制品。

所以：每多打一次包 = 多一次人工升级授权 + 多一次冒烟。四点里三点要改包内文件，把它们拆开就是 3~4 次授权，而中间那些制品没有任何人会部署。

### 5.3 为什么必须等 tag 之后

- v0.2.0 一旦打 tag 并发布，它的制品摘要就是「已授权、已冒烟」的那个精确值（`AGENTS.md` 验证标准 4/5：真实发帖推送冒烟 + 手机 QQ 扫码冒烟）。tag 之前改代码，等于让 tag 指向一个没跑过这两条冒烟的制品，或者逼着把打包与冒烟跑两遍。
- tag 之后再做，`docs/acceptance-0.2.0.md` 那套验收证据仍然对得上它自己记录的摘要，不需要重写。

### 5.4 为什么与模板预设合并

模板预设会动 `template.go` / `manifest/settings.json` / 前端 dist，与 2、3、4 落在**同一批文件**上。合并成一次打包 → 一次摘要变化 → 一次升级授权；拆开则第二次打包的产物几乎必然要重跑 §5 的全套授权流程，且中间版本无人使用。

### 5.5 §11 的固定成本：不要试图「对齐摘要」

`NOTES.md:226+`（§11）已实测：宿主 dev watcher 带 `-ldflags=-s -w` 且走临时 `go.work`（无 replace 行），两个工作流把 replace 重写成绝对路径，`prepare-package.sh` 保持相对 replace——**同一份源码四个不同摘要，属预期**。结论沿用：每批改动只按 release 口径（`prepare-package.sh`）打一次；dev 反复重启导致的摘要跳动按 §11 处置，不当 bug 重查，也不为「对齐」加 `-ldflags`。

### 5.6 现在就能落地、零摘要影响的（纯文档）

已核对清单 `packageFiles` 只有 `backend/plugin`、`schemas/*.json`、`openapi/routes.yaml`、`frontend/admin/dist/settings.{mjs,css}` —— **`docs/` 不在包内**。因此以下可以立刻提交，不触发任何摘要变化、不需要重新授权：

- 本文件 `docs/m1.2-hardening-evidence.md`；
- 同类的 `NOTES.md`、`AGENTS.md`、`README.md`、`docs/plan-qq-bot.md`、`docs/acceptance-0.2.0.md` 的任何增补；
- `.github/workflows/*`、`scripts/*`（不在包内，但会影响 CI 行为，改前仍需跑一次 CI）。

需要等 tag 的只有一件事：**改包内代码**（第 2、3、4 点与模板预设），一次打包完成。
