本文是 `sforum-qq-bot` 插件的**产品任务书**：定义"做什么、不做什么、怎么算做完"。
文中凡涉及 QQ 官方平台的具体接口路径、参数名、频控数值、字段名，一律**不写**——
那属于 researcher 的产出（`docs/qq-api-v2-capabilities.md`）。本任务书只按四类能力标注依赖：

| 代号 | 能力类别 | 含义（不指定接口） |
| --- | --- | --- |
| **T** | 取 token | 用机器人凭据换取访问凭证的类别（获取/续期） |
| **S** | 事件订阅 | 让 QQ 侧把事件推给本插件的类别（长连接订阅 / 回调订阅） |
| **M** | 发消息 | 本插件主动向 QQ 会话投递内容的类别 |
| **R** | 收消息 | 本插件接收 QQ 侧消息并解析的类别 |

## 1. 背景

SForum 是一个插件优先的开源论坛框架，论坛本体（主题、回复、审核、公告、身份与权限）由宿主 Core
拥有，扩展只做协议适配与垂直能力。社区运营目前的主要触点在论坛站内，运营方与核心用户同时活跃在
QQ 群聊/频道，导致两个高频问题：

1. **站内动态出不去**：新帖、精华回复、审核结果、公告停留在站内，QQ 侧用户看不到，运营方需要
   手工复制粘贴转发。
2. **QQ 侧动作进不来**：用户在群里想查帖、回帖，只能先记住论坛网址、切浏览器、登录、再找帖子。

QQ 官方机器人开放平台提供了合规的机器人接入形态（凭据取 token、事件订阅、发消息、收消息四类能力），
是把论坛与 QQ 群/频道连起来的**唯一合规路径**。本插件的目标就是把这条双向通道以"论坛框架的一个
可安装扩展"的形式提供出来。

## 2. 目标

G1. **论坛 → QQ 单向推送**：论坛侧关键事件（新帖、回复、审核结果、公告等）经插件投递到管理员配置
    的 QQ 群或频道，内容可读、可点回原帖。
G2. **QQ → 论坛回流**：QQ 侧消息与 @机器人 指令可回流论坛，覆盖"发帖、回帖、查帖、订阅管理"四类动作。
G3. **最小可用闭环（MVP）**：一个管理员只填 AppID/AppSecret、选环境、填一个群 ID，就能在群里收到
    论坛新帖通知；不需要登录额外控制台、不需要额外数据库、不需要二次开发。
G4. **边界干净**：论坛数据的读写**全部**走宿主公开契约（Event / HostQuery / Host Command）；
    插件不连宿主数据库、不自建业务表、不接管审核流程。
G5. **为多 IM 留口子**：内部通道抽象预留（一个 IM 平台 = 一个适配器实现），但本期**只实现 QQ 一个**
    适配器，不做统一层。

## 3. 非目标（明确不做）

以下条目在本任务书覆盖范围内**明确排除**，实现时不得"顺手做进来"：

| 编号 | 不做的范围 | 原因与替代做法 |
| --- | --- | --- |
| N1 | **不做 QQ 个人号协议**（非官方、非授权的账号协议/逆向协议） | 合规红线。本插件只对接 QQ 官方机器人开放平台的机器人形态 |
| N2 | **不做私域营销群发** | 无授权的批量触达与骚扰。推送只面向管理员显式白名单内的会话，且受事件开关与限流约束 |
| N3 | **不做音视频、语音、文件传输类消息** | 只处理文本类内容；附件/图片类消息仅作为"不可转发"的降级处理，不做媒体搬运 |
| N4 | **不自建审核台** | 审核判定权在论坛侧（宿主审核/治理体系），QQ 侧只**接收结果通知**，不在 QQ 里做审批动作 |
| N5 | **不做多 IM 统一层**（微信/钉钉/飞书/Telegram 同一套抽象与实现） | 本期只做 QQ；抽象层只做接口预留（见 §7.5），不实现第二适配器，不引入通用 IM SDK |
| N6 | 不做 QQ 侧的账号体系、实名、关系链 | 论坛身份在论坛侧；QQ 侧身份只在"命令执行的身份映射"范围内使用（见 OQ-3） |
| N7 | 不做论坛侧的 UI 重建（QQ 内嵌完整论坛客户端） | 只做指令与摘要卡片式交互 |
| N8 | 不做 QQ 商业化能力（广告、裂变、小程序跳转、留资） | 与论坛社区定位无关，且涉及平台合规 |
| N9 | 不做插件自建的用户表/业务表镜像 | 论坛实体数据一律现读现用；插件只允许保存"订阅关系"这类自有投影（见 §7.3） |
| N10 | 不承诺 QQ 平台的富文本/卡片/表情等高级消息能力 | 除非 researcher 结论确认支持，否则 MVP 一律按纯文本 + 链接设计 |

## 4. 用户故事与验收标准

### 4.1 管理员视角

**US-A1 作为论坛管理员，我只想填 AppID/AppSecret 就把论坛动态推到我自己的 QQ 群，不想研究任何技术细节。**

- 验收 A1-1：安装并启用插件后，设置页出现"QQ 机器人"分组，含 AppID、AppSecret、环境三字段，保存后即时显示"凭据有效/无效"状态，且无效时给出可操作的错误说明（不出现堆栈）。
- 验收 A1-2：AppID/AppSecret 留空时，插件**不**发起任何外部连接，面板明确提示"尚未配置凭据，推送已暂停"。
- 验收 A1-3：配置完成后，插件在 30 秒内完成一次连通性自检，面板显示连接状态（未连接/已连接/连接失败+原因）。
- 验收 A1-4：所有设置项都有可一键恢复的推荐默认值；恢复默认不删除已保存的密钥，只重置非敏感项并在界面明确说明。

**US-A2 作为论坛管理员，我希望能选择"哪些论坛事件推送到哪个群"，并且能在误推时立刻停掉。**

- 验收 A2-1：事件开关按事件类型列出（至少：新主题、新回复、主题被隐藏/删除、主题被锁定/置顶、公告、新用户注册），每项可单独开启/关闭，默认只开启"新主题"。
- 验收 A2-2：推送目标按会话类型分别配置（群 / 频道各一份白名单），白名单为会话 ID 列表；不在白名单的会话永远收不到任何推送。
- 验收 A2-3：存在"全局暂停推送"开关，关闭后插件停止一切外发消息（已入队的任务不再投递），并在面板显示剩余队列条数。
- 验收 A2-4：任何一次推送失败（凭据过期、目标不可用、限流）都在面板可见，且不会导致论坛侧操作失败或变慢。

**US-A3 作为论坛管理员，我希望在群发之前先小范围试跑，不要一上线就打扰整个社区。**

- 验收 A3-1：存在"测试发送"动作，向选定目标发送一条带明显"测试"标记的消息，不依赖任何论坛事件。
- 验收 A3-2：存在沙箱/正式环境切换；沙箱环境下即使配置了正式环境凭据也不向正式会话发消息，反之亦然（错误配置时明确失败而不是静默降级）。
- 验收 A3-3：首次启用插件时，默认**不**开启任何推送（推送事件开关默认仅"新主题"开启且目标白名单为空，等价于不推送），并在面板给出"下一步：添加目标会话"的操作提示。

**US-A4 作为论坛管理员，我希望知道每条推送发到哪、为什么失败，出问题能自己排查。**

- 验收 A4-1：面板可查看最近 N 条投递记录（时间、事件、会话目标、结果、失败原因摘要），敏感字段（凭据、完整报文）不出现在记录中。
- 验收 A4-2：可导出投递记录为 CSV（用于排查与留档）。
- 验收 A4-3：面板给出接入模式（长连接订阅 / 回调订阅）与当前生效模式、事件订阅状态、最近一次收到事件的时间。

**US-A5 作为论坛管理员，我不希望 QQ 侧的对话能绕过论坛的权限体系乱发帖。**

- 验收 A5-1：所有回流写操作（发帖、回帖）默认关闭，且必须由管理员显式开启才生效。
- 验收 A5-2：回流写操作受宿主权限与信任等级约束，插件不得绕过宿主校验；权限不足时向 QQ 侧回复"无权限"而不是静默失败。
- 验收 A5-3：所有由 QQ 侧触发的论坛写操作在论坛侧留下可追溯记录（作者身份、来源渠道）。

### 4.2 论坛用户视角

**US-U1 作为论坛用户，我希望在群里就能看到论坛上新帖，并且能点回原帖继续讨论。**

- 验收 U1-1：论坛创建主题后，在白名单群内收到一条消息，包含标题、作者、分类、内容摘要与原帖链接。
- 验收 U1-2：消息中的链接指向真实主题页（不是占位链接），在浏览器中打开即为该主题。
- 验收 U1-3：消息长度受模板与摘要长度限制，超长内容被截断并标注"…"，不会因为一条超长帖子把群里刷屏。
- 验收 U1-4：同一个主题在短时间内多次触发（如编辑后再次触发）不会产生刷屏重复消息（合并窗口可配置，默认开启合并）。

**US-U2 作为论坛用户，我希望在群里 @机器人 就能查到某个帖子的内容，不用切浏览器。**

- 验收 U2-1：@机器人 + 主题 ID/链接，机器人回复该帖的标题、正文摘要、回复数与最近若干条回复。
- 验收 U2-2：查询不到（不存在、无权限、已删除）时统一回复"未找到或无权查看"，不泄露"存在但无权限"与"不存在"的区别。
- 验收 U2-3：查询结果只包含公开可见内容；私密分类、隐藏主题、未授权附件不出现在回复中。
- 验收 U2-4：机器人回复中给出的链接可点回论坛原帖。

**US-U3 作为论坛用户，我希望在群里 @机器人 发一条消息就能回帖，不用重新打字。**

- 验收 U3-1：@机器人 + 回复内容 + 主题链接，论坛上生成一条回复，内容与 QQ 侧一致且保留来源标记。
- 验收 U3-2：用户未被授权（如信任等级不足、主题已锁定）时，机器人明确回复失败原因，论坛侧不产生半成品内容。
- 验收 U3-3：回复内容经过论坛既有内容策略处理（长度、敏感内容、链接去重），插件不得绕过长度与内容规则。
- 验收 U3-4：同一条 QQ 消息重复投递（网络重试）不会在论坛产生两条回复（幂等）。

**US-U4 作为论坛用户，我希望在群里 @机器人 发新帖，且发出来的是正经论坛主题（有分类、有标签、有作者）。**

- 验收 U4-1：@机器人 + 发帖命令 + 内容，成功后机器人回复新主题的链接。
- 验收 U4-2：新帖归属到管理员配置的默认分类；未配置时命令被拒绝并给出明确提示，不静默落到随机分类。
- 验收 U4-3：新帖作者映射遵循管理员选定的身份策略（见 OQ-3），且论坛侧显示的作者与策略一致。
- 验收 U4-4：新帖创建后，论坛侧的反向推送（如"新主题"已开启）不会把它再推回同一个群形成回声（同一会话内可配置去回声）。

**US-U5 作为论坛用户，我希望管理自己关心的订阅，不要被无关消息打扰。**

- 验收 U5-1：支持"订阅当前主题/分类"，订阅关系存于插件自有投影，论坛实体数据不复制。
- 验收 U5-2：支持退订；退订后同一主题的新回复不再推送到该会话。
- 验收 U5-3：订阅管理命令在无权限时失败关闭，且任何用户不能退订他人建立的订阅。

## 5. 功能清单（两档）

每项标注依赖的 QQ 能力类别（**T/S/M/R**，定义见文首）、依赖的宿主契约面，以及优先级。
`P0` = MVP 必需；`P1` = MVP 内可延后；`P2` = 后续迭代。

## 6. 分期（M0–M3）

| 阶段 | 目标 | 内容 | 完成判据 |
| --- | --- | --- | --- |
| **M0 契约与骨架** | 把"不依赖 QQ 结论"的部分全部定死 | 仓库骨架、manifest 声明（观察型事件订阅、后台作业、所需能力与授权）、设置面板 schema（含默认值/敏感标记）、内部通道抽象定义、依赖清单（宿主事件名与 HostQuery 清单）、凭据校验与连通性自检骨架（无外呼） | 设置面板可保存并恢复默认；manifest 通过宿主校验；配置项与本文 §8 一一对应；连通性自检可运行 |

| **M2 回流只读与订阅** | QQ → 论坛读侧打通 | F-20..F-22、F-25、F-40（若结论支持） | 群里 @机器人 查帖返回公开内容摘要；不可见内容不泄露；订阅/退订生效 |

依赖关系：M1 依赖 researcher 给出 T/S/M 的可行结论与限流口径；M2 依赖 R 与公开读契约；
M3 依赖 Core 侧提供写入用的 Host Command（当前**没有**，见 §7.4），以及 OQ-3 的身份策略拍板。

## 7. 边界声明

### 7.1 论坛数据读写只走宿主公开契约

| 方向 | 允许的宿主契约 | 明确禁止 |
| --- | --- | --- |
| 论坛 → 插件 | manifest `events[]` 观察型订阅（`topic.created`、`comment.created`、`topic.updated`、`topic.hidden`、`topic.locked`、`topic.pinned`、`user.registered` 等 Core 事件名） | 直接读宿主数据库；在事件回调里做同步外呼（须转后台作业） |
| 插件 → 论坛（读） | 稳定 HostQuery（如 `core.query.public_topic.by_id`、`core.query.public_comments.list`、`core.query.public_topics.list`、`core.query.public_categories.list`）+ 相应 `core_views` 授权 | 裸 SQL 查询宿主库；以"临时"名义申请 `raw_core` |
| 插件 → 论坛（写） | **原子、可审计的 Host Command**（按 §7.4 落地） | 绕过权限；用 `raw_core` 直接写帖子表 |
| 插件 → 论坛（事件） | 自有命名空间事件经 `sforum.events.emit@1` 发布 | 发布 Core 或他人命名空间的事件名 |
| 插件 → 论坛（其他） | 审计追加、后台作业、通知发射等已有能力 | 私自扩展宿主权限面 |

### 7.2 不碰宿主数据库、不自建业务表

插件**不建立**任何镜像论坛实体的表（帖子、回复、用户、分类、附件均不复制）。允许持久化的只有插件
自有状态，且必须在 manifest 中以 `database.grants: ["own_schema"]` 显式声明：

- 投递记录（用于 §US-A4 的排查与导出）；
- 合并/节流窗口状态；
- 订阅关系（主题/分类 → 目标会话），属于"观察事件 + 自有投影"的合法形态。

自有表的读写**不依赖**宿主数据即可完成，且不与宿主实体建立外键或同步任务。

### 7.3 QQ 侧协议适配是插件的唯一职责

插件负责：QQ 协议适配（鉴权、订阅、消息收发、消息格式转换）、模板渲染、目标路由、限流节流、
指令解析。插件**不负责**：论坛业务规则（长度、内容策略、权限、信任等级）、审核判定、身份体系、
通知中心的站内投递策略。

### 7.4 写侧缺口（必须显式承认）

宿主现有的写入类 Host Command 覆盖审核可见性与治理（可见性、审核评审等），
**不覆盖"创建主题 / 创建回复"**。因此 QQ → 论坛的发帖/回帖不能靠现有契约完成，选项只有：

1. Core 新增受控的写入 Host Command（带幂等键、权限校验、内容策略复核、审计回执）——**推荐**；
2. MVP 只做读侧（查帖），写侧延后到 Core 落地；
3. 插件申请 `raw_core` 直写 —— **否决**（与数据面策略冲突，破坏审计与事务边界）。

在 1 或 2 拍板前，F-23/F-24 保持"默认关闭 + 依赖未满足"的标注，不实现绕过路径。

### 7.5 为多 IM 留口子（预留，不实现）

内部定义平台无关的三段抽象：**平台适配器（鉴权/订阅/收发消息）→ 归一化消息 → 通道路由/模板**。
QQ 是第一个适配器实现。MVP 只要求"接口形状允许替换适配器"，不为假想的多平台需求写通用框架；
不引入第三方通用 IM SDK（除非它同时被 QQ 实现需要）。

分组与默认值遵循"新手可用的安全默认"：所有非敏感项都有推荐默认值并支持一键恢复；

## 9. 验收标准（整体）

1. **闭环验收**：在沙箱环境完成一次完整链路——论坛创建主题 → 白名单群收到含链接的消息 → 群里
   @机器人 查回该主题并得到公开内容摘要 → 群里 @机器人 回帖 → 论坛出现该回复且带来源标记。
2. **不越界验收**：插件源码中不存在对宿主数据库的直连、不存在自建的帖子/回复/用户镜像表；
   论坛侧读写全部落在 §7.1 列出的契约面上。
3. **安全默认验收**：全新安装状态下，插件不向任何会话发送消息；未配置白名单时推送恒为零；
   写侧指令默认关闭。
4. **失败可解释验收**：凭据错误、订阅失败、限流、超时、权限不足，管理员在面板与 QQ 侧分别看到
   可读的原因，不出现原始堆栈。
5. **隐私验收**：日志、投递记录、审计条目中不出现 AppSecret、访问凭证、完整原始报文（除非管理员
   显式开启该开关）、未授权的私密内容。
6. **不拖垮论坛验收**：推送与指令处理全部异步（事件观察 → 后台作业），论坛写路径不因 QQ 侧
   超时或故障而变慢或失败；QQ 侧不可用时论坛功能完全不受影响。
7. **幂等验收**：同一事件重复投递、同一 QQ 消息重复处理，均不产生重复推送或重复回复。
8. **可移植验收**：更换 QQ 适配器实现不影响论坛侧行为（§7.5 抽象成立的最弱证据）。

### 9.1 MVP 完成定义（DoD）

MVP 档（F-01..F-17 全部 P0 项 + F-20..F-22 + F-30..F-32）达成以下条件才算"可用"：

1. 管理员按 §8 填写 AppID/AppSecret、选环境、填至少一个群 ID、开启"新主题"事件开关后，
   论坛创建主题 → 该群收到一条含标题、作者、分类、摘要与原帖链接的消息（US-U1 全部 4 条验收通过）。
2. 群里 @机器人 查帖能返回公开内容摘要，且不可见内容不泄露（US-U2 全部 4 条验收通过）。
3. 新安装状态下推送为零、白名单为空时推送为零、写侧指令关闭（验收 3、验收 8）。
4. 面板能看到连接状态、事件开关状态、最近投递记录与失败原因；凭据错误时 30 秒内可见明确提示。
5. 一键恢复推荐默认值可用，且不删除已保存的密钥。
6. 全部失败路径（凭据错、订阅断、限流、权限不足）都不影响论坛侧的正常发帖与回帖。

### 9.2 后续迭代档的验收原则

- 每个迭代项独立可上线、独立可回滚，不依赖后续迭代项。
- 引入新消息形态（富文本/卡片/图片）时，必须先有 researcher 结论支撑，并补一组"形态降级"用例：
  平台不支持或被拒绝时，回落为纯文本 + 链接，而不是丢消息。
- 写侧相关项（F-23、F-24、F-25）在宿主写入命令落地前保持关闭；启用时必须同时具备
  权限校验、幂等键、审计回执与失败提示四项证据。

## 11. 需要 YG 本人拍板的问题（不等 research）

1. **QQ 侧回流写的身份模型**：QQ 用户 → 论坛作者的映射采用哪种？
   (a) 管理员维护"QQ 标识 ↔ 论坛账号"白名单；(b) 以固定机器人/运营账号身份发帖，QQ 侧仅作为输入渠道；
   (c) 在论坛侧新增账号绑定入口由用户自助绑定。
   取舍：(a) 最省事但要人工维护；(c) 体验最好但要在论坛加一条绑定流程，属于 Core 侧产品改动。
   **默认建议**：MVP 走 (b)，M2 之后评估 (a)，(c) 单独立项。
2. **写侧依赖的处理方式**：QQ 回流发帖/回帖依赖宿主新增写入类 Host Command（当前没有，见 §7.4）。
   取舍：(a) 先在 Core 加写入命令，本插件等它；(b) MVP 只做读侧（查帖），写侧延后；
   (c) 插件走 `raw_core` 直写。**默认建议 (b)**，(a) 作为 Core 排期项，(c) 否决。
3. **默认推送粒度与噪音策略**：新主题默认推送是否合理、是否默认开启新回复、是否强制合并窗口。
   取舍：默认全开会造成刷屏与限流风险；默认全关会让"装完没反应"。**默认建议**：默认仅开启
   "新主题" + 合并窗口 60 秒 + 合并节流强制启用，其余事件默认关闭，由管理员逐步打开。
