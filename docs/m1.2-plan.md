### 2.2 为什么只打一次包（成本算术）

改包内任何文件 → 树摘要变 → 旧信任失效 → 必须重走「授权当前精确制品 → 确认并升级」
（`NOTES.md` §5 第 2 条；`AGENTS.md` 硬边界 3）。这一步是**固定成本，与改动大小无关**。

- 拆开做：②③④⑤ = 4 次打包 + 4 次授权 + 4 次冒烟，而中间三个制品没有任何人会部署（取证 §5.2）。
- 合起来做：1 次打包 + 1 次授权 + 1 次复验。
- 别试图「对齐摘要」省一次：同一份源码在本机/CI/宿主 dev 下是不同字节（`NOTES.md` §11.4 处置）。
  该节的数值正在按 task-4 重写，本计划只引处置、不引数字。

### 5.2 怎么不破坏 `maxMessageChars` 的「0 = 沿用默认」

这是本批**唯一**会误伤的既有约定，必须写成硬规则：

- 只让**字符串字段**变 presence-aware（`template`、`signature`）。整型分支原样保留：
  `routes.go:254-257` 的 `if limit, ok := routeIntValue(...); ok && limit > 0` 与
  `tool.go:209-212` 的 `draft.MaxMessageChars != nil && *draft.MaxMessageChars > 0`。
- **禁止**顺手做「通用 presence-aware 重构」：一旦整型也改成「有键即生效」，`maxMessageChars=0` 会真的传 0，
  而 `clampText` 对 `limit<=0` 直接返回原文不截断（`tool.go:415-418`），清单里「0 表示沿用默认」
  （`schemas/preview-input.json` 的 `maxMessageChars` 描述、`settings.json` 默认 `1000`）当场失效。
- 守卫：`TestRoutePreviewMaxCharsZeroUsesDefault`（`routes_test.go:514`）**不许改**；再加
  `TestRoutePreviewEmptyTemplateKeepsMaxCharsConvention`（§4.2）把两条约定的共存钉住。
- 已有先例可照抄：`excerptLimit` 已经是 presence-aware 整型（`routes.go:251`，`0` 表示不显示摘要），
  两者能在同一函数里共存——这正说明「字符串 presence-aware + 整型保留 0 语义」不是折中，而是现有形态。

## 7 上游 issue 清单（问题 G，可直接贴）

四条，每条都是「宿主行为 + 我们无法在插件侧解决」。提交渠道由 lead/YG 定（本仓库不改宿主）。

### I-1 设置页探测链路没有 actor，导致同一批副作用有两个权限口径

- **现象**：`tech_admin`（默认角色，持 `extension.plugin.manage`、不持 `sforum.qq-bot.manage`）在设置页点
  「发一条测试消息」能真的往群发一条、点「推送状态」能看到完整 `group_openid`；但它调不动插件路由 `/test-push`。
- **证据**：`app/Models/Extensions/settings_actions.go:17-94`（闸是 `canManageExtensionSettings`）、
  `app/Support/Extensions/settings_actions.go:28-47,72-107`（探测链路无 actor 参数）、
  `app/Models/Identity/seeds.go:228-243`（`tech_admin` 的权限项）、
  `app/Support/Routes/core_guard_authorizer.go:341-354`（路由链路的闸）。
- **期望**：给 `ai_tool_probe` 的调用带上 actor 事实（首选），或在 UI/文档里明示「探测按钮的权限面是
  `extension.plugin.manage`，与插件路由的权限键不同」。
- **不修的代价**：插件的「谁能发真消息」取决于入口，运营无法从权限矩阵推断。

### I-2 `sforum.ai.tool.invoke.request@1` 不携带 actor / purpose 事实

- **现象**：插件收到的 `AIToolCall` 在探测链路与模型链路形状完全一致，`Context.Actor` 恒为 nil，
  插件在结构上无法实现任何工具级授权。
- **证据**：`app/Support/Extensions/protocol_v2_ai_tool.go:94-105`（payload 只有 `name/arguments`，
  可选 `locale/topicId/viewerUserId`）、`app/Support/Extensions/protocol_v2_client.go:772-789`、
  SDK 把「不带 actor」钉成不变量：`sdk/plugin/v2/ai_tools_test.go:27-28`。
- **期望**：契约里增 `purpose` 与 actor 事实（哪怕是只读的 `viewerUserId` 之外的真实操作者），
  或在契约文档里明确写「AI 工具调用没有授权语义，安全边界由宿主白名单负责」——现在这句话只存在于 SDK 测试里。
- **不修的代价**：任何需要「谁在调用」的工具都只能靠宿主白名单兜，插件无法自证。

### I-3 用途白名单只校验工具名语法，不区分「管理员工具」

- **现象**：运营在站点 AI 设置里把 `qq-bot-test-push` 写进某个用途的白名单就能保存成功，
  此后模型可以真的发群消息，且无 actor 闸（I-2）。
- **证据**：`app/Support/AI/validation.go:39-58`（只校验长度/`ValidToolName`/去重）、
  `app/Support/AI/tool_loop.go:275-296`（`registry.Lookup` + `toolAllowed` 双闸）、
  `bootstrap/ai_plugin_tools.go:105-124`（登记不等于暴露）。
- **期望**：清单支持标记「该工具需要管理员权限」，白名单校验时拒绝未授权的管理员工具；
  或至少在保存白名单时给出「这是管理类工具」的确认。
- **不修的代价**：默认安全，但一次配置漂移就把「模型调不到」变成「模型能发真消息」。

### I-4 树摘要把 `node_modules` 算进制品，dev watcher 与信任校验互斥

- **现象**：`VerifiedTreeDigest` / `DigestTree` 走 `collectDigestFiles(root,false)`，不跳过 `node_modules`
  且拒绝符号链接；作者树 `DigestAuthorTree` 才跳过。于是「装依赖 → 打包」必然摘要不符，
  「删依赖 → dev watcher 的前端构建 exit 127」。
- **证据**：`app/Support/ExtensionPackage/digest.go:35,41-48,72-130`、
  `verification_cache.go:48-56`、`dev_build.go:477-485`（`BuildFrontend` 只跑 `bun run build`，跳过依赖安装）。
- **期望**：`DigestTree` 也对 `NonArtifactDirectory` 跳过（发布 zip 本就不含这些目录），
  或在文档里明确「作者树与制品树不是同一套遍历规则」的处置流程。
- **不修的代价**：每个用预构建前端的扩展都会撞一次，且错误信息指向「摘要不符」而不是「依赖目录参与了摘要」。
