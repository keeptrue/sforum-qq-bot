## 0. 前置检查（四条都过再开始）

### 0.1 宿主扫到了本仓库

`SForum/.env:65` 的 `EXTERNAL_EXTENSION_ROOTS` 最后一个路径必须是本仓库根
（`/home/inkedus/Code/github/sforum-qq-bot`），宿主按 `<根>/plugins/<包目录>` 扫描。
改过这行之后要**重启 API 进程**（`127.0.0.1:8080`）才会重新扫描，热重载不算。

看：后台 →「扩展」→「插件」。

- 成功：列表里有「QQ 机器人」卡片，版本 `0.4.2`。
- 失败长什么样：列表里根本没有这张卡片 → `.env` 那行路径写错、或 API 没重启。
  路径写错时宿主不会报错，只会静默少扫一个源。

### 0.2 插件已启用

同一张卡片上的启用开关必须打开。没启用时插件后端不在线，页面上发出的每个请求都会落到
「route」类横幅：「先在插件列表启用本插件，再回来绑定。」（插件已启用却仍出现这条，
就看它下面那句提示：后端没随保存重启）。

### 0.3 当前生效的制品摘要能对上

宿主按清单里的摘要与实际二进制比对，对不上就拒绝启用（或要求重新授权）。
第一条命令里 `"digest"` 那一行的 64 位值，必须与第二条命令打印的 64 位值逐字相等：

```bash
# 清单里记录的摘要（看 "digest" 那一行）
grep -A1 '"backend": {' plugins/sforum-qq-bot/sforum.extension.json
# 磁盘上二进制的真实摘要
sha256sum plugins/sforum.qq-bot/backend/plugin
```

本轮实测两边都是 `904b5c2805abfb184c4405439dd0cbed437d518f27ae70dda9e0c67071809f2f`。

- **后台不显示 `backend.digest`**，任何界面都没有它（在宿主根跑
  `rg 'backendDigest|backend\.digest' apps/web` 零命中）。
  后台能看到的是**包摘要**：授权卡显示完整 `packageDigest`
  （`apps/web/app/components/admin/SFAdminExecutableTrustImpact.vue:217-218`，由
  `SFAdminExtensionEnableDialog.vue:156` 挂上去），升级卡**在内容更新时**显示包摘要前 8 位
  （`apps/web/app/utils/admin/extensions/updatePresentation.ts:52-55` 的 `shortDigest`、
  `apps/web/app/pages/admin/extensions/index.vue:666-671`，纯版本升级不显示摘要）。
  两者都不是 `backend.digest`，**不要**拿它们与清单里的值比；`backend.digest` 只以那两条命令为准。
- 不相等时**不要手改清单**：跑一次 `./scripts/prepare-package.sh`，再走
  「授权当前精确制品 → 确认并升级」。宿主 dev watcher 在开发机上重建出来的二进制
  摘要天然与发布口径不同，那是正常现象，见 `NOTES.md` §11。

### 0.4 账号与权限

用超级管理员登录。未登录访问 `/control-panel` 会跳到登录页，目标路径放在 `redirect` 查询参数里
（宿主 `app/Http/route_dispatcher.go:483` 拼的是 `/login?redirect=` + URL 编码后的目标，形如
`/login?redirect=%2Fcontrol-panel`）。

绑定、测试消息、推送状态这三件事都需要 `sforum.qq-bot.manage` 权限；普通管理员
没这个权限时，设置页会显示「当前账号没有这个插件的管理权限。」

> **✓ 通过判据（前置检查）**
>
> - 「扩展 → 插件」里能看到「QQ 机器人」，版本 `0.4.2`，开关是开的
> - `sha256sum` 与清单 `backend.digest` 逐字相同
> - 超级管理员已登录，能进「扩展 → 插件」页面

## 1. 步骤一：扫码绑定 AppID / AppSecret

进入后台 →「QQ 机器人」菜单项 → 设置页顶部的「绑定 QQ 机器人」卡片。

1. 点「扫码绑定」。卡片先显示「正在生成二维码…」。
2. 出码后卡片显示二维码，旁边（窄屏会换行到下方）一行「用手机 QQ 扫码，然后在手机上确认授权。」
   和一个从 `10:00` 开始走的倒计时（等待态布局在 `bind-card.ts:117-138`；倒计时起点在 `:270`
   `expiresAt = Date.now() + ttlSeconds(response.expiresInSeconds) * 1000`，而 `expiresInSeconds`
   来自 `/bind/start`，即 600 秒）。
3. 手机 QQ 扫码 → 手机上点确认授权。
4. 卡片变成「扫码成功，正在保存凭据…」，随后显示「已绑定并保存」+
   「当前 AppID：`APP_ID`」，并弹一条同名 toast。
5. 看下方表单：「AppID」已填好真实值；「AppSecret」是空的——这不是没保存，
   而是宿主对 secret 字段掩码回空。已保存的 secret 也不会在任何地方回显。

**这张卡片自己会保存，不需要再点页面底部的「保存」。** 只有出现
「扫码成功，但自动保存没有生效，请检查后在页面底部手动保存。」时才需要手动补一次。

失败长什么样：

- 等太久没扫：卡片变「二维码已过期，请重新生成。」+ 按钮「重新生成二维码」。
  二维码有效期 10 分钟（`backend/bindstore.go:13` 的 `bindTaskTTL`，`/bind/start`
  返回的 `expiresInSeconds` 就是它）。
- 轮询连续 3 次失败：卡片变「绑定流程没有走通，请重试；也可以直接手动填写凭据。」
  （`MAX_POLL_FAILURES = 3`，`frontend/admin/src/bind-card.ts:11` 与 `:232-235` → `i18n.ts:17`）。
- 点太快：后端确实回 429，响应里也带「扫码绑定请求过于频繁，请稍后再试。（约 N 秒后可再试）」
  （`backend/routes.go:89-91`），但**这句原文不会出现在页面上**——组件在请求失败时只按 HTTP
  状态换横幅（`frontend/admin/src/app.ts:137-139` 的 catch → `classifyError` `:58-67`），429 落到 rate 横幅：
  「操作太频繁，被插件侧的限流挡住了。」+「等几秒再试；连续点「重新生成二维码」或反复触发
  预览会撞同一道限流。」（`i18n.ts:67-68`）；同时卡片翻成「绑定流程没有走通，请重试；也可以
  直接手动填写凭据。」（`bind-card.ts:285-289` → `i18n.ts:17`）。后端那句只存在于接口响应里
  （这条分支不写日志），想核对就抓 `/bind/start` 的响应，页面上是看不到的。
- **secret 只交付一次。** 在「扫码成功，正在保存凭据…」这一步刷新页面、关标签或断网，
  这次取到的 AppSecret 已经作废，只能重新扫码（或改用手动填写）。
  绑定过程中不要刷新页面。
- 扫码接口没就绪（插件刚重启）：后端回 503 与「扫码绑定服务尚未就绪，请重启插件后再试，
  或直接手动填写凭据。」（`routes.go:81-82`、`:113-114`），这句同样**不上屏**；页面上是
  service 横幅「插件服务暂时不可用。」+「后端可能刚重启或返回了错误；稍后再试，原始错误不会
  显示在这里。」（`i18n.ts:69-70`），卡片翻成「绑定流程没有走通，请重试；也可以直接手动填写
  凭据。」（`bind-card.ts:263-267`、`:285-289` → `i18n.ts:17`）。

不想扫码就点「手动填写凭据」：把 QQ 开放平台里的 AppID / AppSecret 填进表单，
点页面底部「保存」。AppSecret 只填这一次，之后留空即表示沿用已保存的值。

> **✓ 通过判据（步骤一）**
>
> - 卡片停在「已绑定并保存」，且显示「当前 AppID：`APP_ID`」
> - 下方表单 AppID 有值、AppSecret 为空
> - 刷新页面后 AppID 还在（说明是宿主真的保存了，不是页面内存里的值）

## 2. 步骤二：当前账号卡片

设置页最顶部有一张「当前账号」卡片，用来直接看「现在连的是哪个机器人、连没连上」，不用再点
「推送状态」读一大段文本。

1. 进页面就自动拉一次（`account-card.ts:239`）。卡片显示头像、昵称、`AppID` 和一枚连接状态徽标，
   下面一行是「已识别群 N · 白名单 M」。
2. 徽标只有五种：**已连接**（绿）/ **连接中**（黄）/ **未启用**（灰）/ **授权失败**（红）/
   **连接异常**（红）。还没配凭据时，徽标位置直接写「尚未配置凭据」（`i18n.ts:9-14`）。
3. 徽标下面可能跟一句原因（最近一次的错误），没有原因就不显示。
4. 「已识别群 N · 白名单 M」在白名单非空时可以点，点一下跳到「群 ID 列表」输入框。
5. 点右上角「刷新」手动重拉。注意 `GET /users/@me` 有缓存：**10 分钟内不会真的重查**（失败只缓存
   1 分钟），所以刚改完头像或昵称、刷新看不到变化是正常的（`accountstatus.go:11-17`）。

失败长什么样：

- 徽标红或灰 → 先查凭据与网络。灰（未启用）多半是「启用群 ID 自动识别」关着；红（授权失败 /
  连接异常）看它下面那句原因，常见是 AppSecret 不对、平台侧限制或网络不通。
- 徽标**绿但 @ 不回** → 不是连接问题，去看步骤五的回复逻辑（开关、60 秒闸、日志里那行「@ 回复失败」）。
- 卡片写「状态暂不可用」→ 这次 `/account/status` 没成功（后端没升级或请求失败）。这是卡片级降级，
  **不弹**页面横幅；上一轮的数字会留在原位，别当成实时值。
- 昵称/头像不显示、只剩 `AppID` → 机器人信息拉不到（`/users/@me` 失败），连接状态与 `AppID`
  不受影响（`account-card.ts:157-160`）。

> **✓ 通过判据（步骤二）**
>
> - 卡片显示头像与昵称，`AppID` 与下方表单里的一致
> - 徽标是「已连接」（绿）；凭据没配时应当是「尚未配置凭据」
> - 「已识别群 N · 白名单 M」两个数字与「推送状态」里的一致

## 3. 步骤三：拿到群 ID 并填进白名单

群 ID 是机器人视角的 `group_openid`，**不是**你在 QQ 里看到的群号，抄错一个字符就发不出去。

1. 「推送目标」组里确认「启用群 ID 自动识别」是开的（默认开），点页面底部「保存」。
2. 把机器人拉进目标群，或者在群里 @ 它一次。这一步只是让插件看见一次群事件。
3. 点页面底部「推送状态」。输出块里会出现一段：

   ```
   最近识别的群 ID（完整，可复制到白名单）：
   <group_openid>（<事件类型>，11-18 02:10，1 次）
   ```

   整块状态的行序是固定的（`backend/tool.go:233`、`:251`、`:255`、`:264`、`:287`）：

   ```
   第 1 行  QQ 推送状态
   第 2 行  凭据：已配置｜目标群：N 个｜暂停：否｜群 ID 识别：开｜队列：0 条
   第 3 行  长连接：connected（已连接 1 分 20 秒）    ← 状态值 + 「最近错误」都在这一行
   之后     最近投递：…                              ← 最多 10 条
   之后     最近识别的群 ID（完整，可复制到白名单）：…  ← 最多 10 个
   ```

4. 复制这一整串 `group_openid`，粘进「群 ID 列表」（多行文本框）。多个群就一行一个；
   以 `#` 开头的行是注释，空行直接忽略：

   ```
   ABCDEF0123456789ABCDEF0123456789
   # 备用群
   0123456789ABCDEF0123456789ABCDEF
   ```

5. 点「保存」。

失败长什么样：

- 状态里写「（暂无记录：机器人被拉进群或群里 @机器人 后会出现在这里）」——三种原因：
  机器人不在群里（或已被移出）/ QQ 开放平台的群事件订阅权限还没批（只能去平台申请，
  没批下来就只能手动填群 ID）/ 长连接没连上（看状态第 3 行）。
- 状态第 3 行就是长连接状态（第 1 行是标题、第 2 行是凭据与目标群那一行，别数错）。这一行的
  状态值只有五种：`disabled`（识别开关关着）/ `connecting` / `connected` / `unauthorized`
  （凭据被平台拒）/ `error`（`backend/gateway.go:34-38`）。**只有 reason 非空时才追加**
  「，最近错误：…」（`backend/tool.go:259-261`）：`connecting` 与开关关闭的 `disabled` 都是空
  reason（`gateway.go:200`、`:139`），所以常见形态只有状态值本身；`unauthorized` / `error`
  才一定带原因（`gateway.go:212`、`:215`、`:217`）。不是 `connected` 时，第 2 步的群事件根本
  收不到，先解决长连接。

> **✓ 通过判据（步骤三）**
>
> - 「推送状态」里至少有一行完整 `group_openid`
> - 白名单保存后，再看状态第 2 行（凭据那一行）里的 `目标群：N 个`：N 是**去重后**的条数——
>   注释行、空行不算，重复的群 ID 只算一次（`backend/config.go:159-176` 的 `splitSettingList`）

## 4. 步骤四：勾选已识别的群

插件把收到的群事件记在内存里，设置页可以直接把它们勾进白名单，不必手抄 `group_openid`。

1. 进「推送目标」组。「群 ID 列表」文本框**正上方**有一块「已识别的群」卡片（`app.ts:241-242`
   把它插在 `data-key="group_ids"` 前面），进页面时会自动读一次。
2. 点卡片右上角「刷新」。读取期间按钮变「刷新中…」、卡片下方写「正在读取…」；成功后按最近活跃
   倒序列出群，底部状态行写「群列表已刷新，共 N 个」。
3. 每行是「复选框 + 群名 + 最近活跃 <时间> · <N> 次事件」。群名拿不到时显示 `openid` 前 6 位加
   `…`，鼠标悬停能看到完整 `openid`（`groups-card.ts:157-165`）。
4. 勾选一个群＝往「群 ID 列表」追加一行它的 `openid`；取消勾选＝只删掉那一个（一行里写了多个
   ID 时保留其余），你手写的行与 `#` 注释都不动（`groups-card.ts:49`、`:58`）。复选框状态每次
   从文本框内容反推、不单独存，所以手改文本域后勾选会跟着变。
5. 勾完点页面底部「保存」，再点「推送状态」核对第 2 行的 `目标群：N 个`。

识别到的群达到保留上限时，卡片会提示「只保留最近 20 个」（数字来自 `/groups/list` 返回的
`recordingLimit`，当前环形容量 20）。

失败长什么样：

- **群名显示不出来是正常的。** QQ 的群信息接口（`GET /v2/groups/{openid}/info`）需要平台把应用
  加进白名单，普通应用会拿到 11253；插件把这种失败当成「暂时没名字」，只让该群回落成 ID 前缀，
  勾选、保存、推送都不受影响（拿不到就返回 `name=null` + `nameUnavailable=true`，`routes.go:311-335`；
  11253 归为确定性失败、缓存 10 分钟，`grouplist.go:107-118`）。
- 卡片写「还没有识别到群。把机器人拉进目标群，或在群里 @ 它一次，再点刷新。」→ 插件还没收到任何
  群事件，原因同步骤三那三种。
- 卡片写「群 ID 自动识别没有打开，插件不会记录群事件。勾选下方的「启用群 ID 自动识别」，再点
  刷新。」→ 开关关着。
- 卡片写「群列表暂不可用，仍可手动填写群 ID」→ 路由不存在（后端还没升级）或请求失败。这是
  卡片级降级，**不会**弹页面级横幅，也不挡保存（`groups-card.ts:215-222` 的降级渲染、
  `:244-247` 的 catch）。

> **✓ 通过判据（步骤四）**
>
> - 「已识别的群」里至少有一行；勾选后「群 ID 列表」多出对应的 `openid`
> - 取消勾选后那一行消失，而你手写的行与 `#` 注释仍在
> - 保存后「推送状态」第 2 行的 `目标群：N 个` 与文本框里去重后的条数一致

## 5. 步骤五：@ 机器人会回一句

0.4.0 新增的入站能力：群里 @ 机器人时，它会用那条消息的 `msg_id` 回一句固定说明（被动回复，
不占主动推送的频控）。

1. 在目标群里 @ 机器人（内容随便），发出去。
2. 几秒内群里应出现一条回复：「本机器人只做 SForum 论坛新帖推送；这个群已记录，可在后台勾选为
   推送目标。」（`gateway.go:68` 的固定文案，不是设置项）。
3. 回设置页点「刷新」（或等 30 秒轮询），「已识别的群」里应出现这个群。

边界（官方口径 + 插件自己那道闸）：

- 被动回复只在 **5 分钟内**有效、同一条消息最多被回 **5 次**（`msg_id` 与 `msg_seq` 联合去重）。
  插件把 `msg_seq` 固定成 1，所以同一条 @ 只会回一次。
- 同一个群 **60 秒内只回一次**（进程内闸，重启即清空）：60 秒内连 @ 两下，第二下不会有回复。
- 关掉「被 @ 时回一句说明」（`reply_on_mention`，默认开）后只记录群 ID、不回复。
- 回复失败**不影响**群 ID 认领：认领先做，回复失败只写一行日志。

失败长什么样：

- 完全没回复：先看步骤二的徽标——红/灰说明根本没连上；绿的话再查「被 @ 时回一句说明」是不是被
  关掉了，以及插件日志里有没有「@ 回复失败」。
- 回了但明显变慢：网关读循环在发送期间不读新事件（单次上限 5 秒，`gateway.go:57-63`），属预期。
- 群里出现平台报错而不是这句说明：看日志里的 `err_code`——被动回复窗口过期是 `40034005` / `304103`，
  同一条消息已被回复过是 `40054005`，机器人已不在群是 `40034101` / `40054003`。

> **✓ 通过判据（步骤五）**
>
> - @ 机器人后几秒内收到那句固定说明
> - 60 秒内再 @ 一次不会重复回
> - 「已识别的群」里能看到这个群（说明认领没被回复失败拖累）

## 6. 步骤六：预览的两种模式

预览卡在「消息模板」组里，有两种口径，默认那种就是「现在真的会发出去的样子」。

1. **默认「将实际发送」**：徽标写「将实际发送」，渲染用的是**已保存配置**——后端走的是与真实
   推送同一个渲染入口（`routes.go:243`、`:250-253` 的 `renderSaved`，推送侧在 `hook.go:94`），
   所以看到的就是下一次推送会发出去的内容。
2. **改了表单但没保存**：预览卡出现提示「草稿与已保存配置不同，当前预览是按已保存配置渲染的；
   点保存后才会这样发出去。」和一个「按草稿预览」按钮。
3. **点「按草稿预览」**：徽标变「草稿预览」、提示变「当前预览按草稿渲染，还没有保存；点保存后
   才会这样发出去。」、按钮变「按已保存预览」，预览跟着草稿走。保存成功后自动切回「将实际发送」。
4. **保存失败时提示不会消失**：基线来自服务端回显（`/preview source=saved` 响应里的
   `savedSnapshot`，`routes.go:218-229`），不是页面上那份草稿；宿主 `save()` 失败并不 reject，
   所以组件不会误以为已经存上——脏提示保留，避免「其实没保存却显示已保存」。
5. **样例数据**：「样例数据」面板可折叠，五个字段（标题 / 作者 / 分类 / 摘要 / 链接）填哪个用哪个，
   留空沿用内置样例；摘要仍按上面的「摘要长度上限」截断。用了自定义样例时，预览区会显示
   「当前用你的样例数据渲染」。

失败长什么样：

- 预览区只写一行「预览暂时不可用；保存后推送仍会正常渲染。」→ 这次预览请求没成功。这是预览区
  自己的降级，不弹页面级横幅，也不影响保存与真实推送。
- 清空模板后预览显示「（模板为空，渲染结果也是空的）」→ 正常。0.2.0 里这个场景会错误地显示
  已保存模板的渲染结果，0.3.0 已修（`routes.go:365`、`:388` 与 `tool.go:349-372` 的
   presence-aware 解析）。

> **✓ 通过判据（步骤六）**
>
> - 刚进页面时徽标是「将实际发送」
> - 改模板但不保存 → 出现「草稿与已保存配置不同…」提示与「按草稿预览」按钮
> - 点「按草稿预览」→ 徽标变「草稿预览」、预览跟着草稿变；点「保存」→ 提示消失、徽标回到
>   「将实际发送」
> - 展开「样例数据」填一个标题 → 预览里的标题变成你填的，并出现「当前用你的样例数据渲染」

## 7. 步骤七：发一条测试消息

**先点「保存」，再点「发一条测试消息」。** 当前生效的**组件**里，「发一条测试消息」与
「推送状态」都走插件路由、按**已保存的配置**执行（`footer.ts:138`、`:159` →
`backend/routes.go:174`、`:207-209`），页面上还没保存的草稿不参与——所以改完内容忘了保存，
测出来的还是上一版。组件自己的提示也是这么写的：「测试消息与推送状态都按已保存的配置执行」
（`frontend/admin/src/i18n.ts:47`）。

清单里那几段描述（`manifest/settings.json:53`、`:107`、`:338`）写的是「用草稿值」——它们描述的是
**表单回退渲染器**下的三个 `ai_tool_probe` action（`useDraftValues: true`，由 AI 工具
`test_push` 执行；那条路径会用表单草稿覆盖已保存值，`backend/tool.go:108-129`）。两种口径说的
不是同一条代码路径：组件用路由，回退渲染器用 AI 工具。按组件操作，就以「先保存再点」为准。

期望看到（输出块是页面底部「保存与测试」卡片里的那块等宽文本，toast 由宿主弹出、位置随宿主主题；
下面这段是按默认模板渲染的样子，模板改过就按你的模板走）：

```
【新帖】【测试】这是一条来自 SForum 的推送样例
作者：示例作者｜分类：示例分类
这里是摘要占位：真实推送时这一段会换成主题正文的开头。
https://forum.example.com/t/10001
来自 SForum 论坛

—— 发送结果 ——
已发送到群 ABCDEF…（message id 1234abcd…）
```

同时群里收到同一条样例消息（两侧文字一致，只有群 ID 是掩码、message id 是前缀）：
群 ID 只留前 6 位再加 `…`（`backend/qqclient.go:422-429` 的 `maskGroupID`），message id 只留
前 8 位再加 `…`（`qqclient.go:431-439` 的 `messageIDPrefix`，`…` 来自 `routes.go:198` 的格式串）。
不足 6 / 8 位时按原样显示、不补 `…`。
测试消息只发给白名单里的**第一个**群，不写投递记录、不改设置。

常见失败文案（原样出现在「发送结果」下面）：

| 现象 | 输出块里的原文 |
| --- | --- |
| 白名单为空 | `未发送：群白名单是空的，请先填写至少一个群 ID。` |
| 凭据缺失 | `未发送：尚未配置 AppID / AppSecret。` |
| 群 ID 抄错 / 机器人不在群 / 群主关了主动推送 | `发送失败：主动消息受限：可能群主关闭了「主动推送消息」（err_code 304023）` |
| AppSecret 错或换过 | `发送失败：凭据无效：AppID 或 AppSecret 不正确，或机器人已不存在（err_code 100007）` |
| 发得太快 | `发送失败：主动消息已超出频控，请降低推送频率（err_code 40034100）` |
| 单条太长 | `发送失败：消息过长，平台拒绝了本次投递（err_code 40054007）` |
| 其它平台拒绝 | `发送失败：QQ 接口拒绝了本次请求（err_code N）` |

「（err_code N）」不是固定文案：`QQError.AdminMessage()` 只在 `Code != 0` 时追加
（`backend/qqclient.go:58-67`，追加在 `:63-65`），所以没有错误码的失败只有原因、没有括号。上表第三行的
`304023` 与 `40034128` 共用同一条文案（`qqclient.go:358-359` 的同一个 `case`），
看到其中任一码都读作「群主可能关了主动推送」。

失败时 toast 是「测试消息没有发出」，成功是「测试消息已发出」。

> **✓ 通过判据（步骤七）**
>
> - 输出块最后一行为 `已发送到群 …（message id …）`
> - 群里实际收到这条样例，文字与输出块一致
> - toast 显示「测试消息已发出」

## 8. 步骤八：真帖推送（端到端）

1. 换一个窗口（或另一个账号）在站内发一篇新主题。白名单群会收到一条按模板渲染的推送。
2. 回到后台设置页，点「推送状态」。输出块的「最近投递：」部分应出现一行：

   ```
   11-18 02:10 成功 ABCDEF… 《帖子标题》
   ```

   失败是「失败」并带上原因；消息被截断会在标题后标「（已截断）」。
   群里只收到消息本身，这一行记录才是核对依据。

**去重窗口 1 小时。** 同一篇帖子（同一投递键或同一主题 ID）在 1 小时内再次触发
不会重复推送，也**不会**写进「最近投递」——它是被静默接受后跳过的。
所以「帖子发了、群没收到、状态里也没有新记录」，先排除是不是 1 小时内重复触发
（编辑后重发、事件重投都算），不要直接判失败。

其它「静默跳过」的情况（都不写记录，只进插件日志）：

| 跳过的原因 | 对应设置项一眼可见 |
| --- | --- |
| `paused` | 「暂停推送」开着 |
| `credentials_missing` | AppID / AppSecret 没配 |
| `whitelist_empty` | 「群 ID 列表」是空的 |
| `category_filtered` | 「只推送这些分类」里没有这篇帖子的分类 |
| `duplicate` | 1 小时内同一帖 |

护栏（默认值，验收时一般不会撞上）：

- **每分钟最多 20 条是全局额度，不是单群额度。** 默认值来自 `backend/config.go:22` 的
  `defaultMaxPushesPerMinute`；插件里只有一个令牌桶，所有群共用、匀速回填
  （`backend/dispatcher.go:62`、`:86`、`:366-386`）；超出的消息排队等待而不是丢弃。设置项
  `max_pushes_per_minute` 的说明写的也是「全局每分钟最多发多少条」
  （`manifest/settings.json:275-279`）。
- **单群每日 800 条**（`backend/config.go:21` 的 `defaultDailyPushCapPerGroup`）。触顶后当天不再
  给这个群发，记录里那一行是 `失败 ABCDEF… 《标题》：quota_exceeded`
  （`dispatcher.go:195-198` 写入，`tool.go:274-283` 渲染）。
- 投递记录是**内存环**：最多留 50 条（`backend/state.go:10` 的 `deliveryRingSize`），状态页只渲染
  最近 10 条（`tool.go:265`），进程重启即清空。所以「状态里没有」不等于「没发生」——先确认它是不是
  被 50 条的环挤掉了，再看插件日志。

> **✓ 通过判据（步骤八）**
>
> - 新发的主题，白名单群收到推送，且文案与设置页模板一致
> - 「推送状态」的「最近投递」里出现这条 `成功` 记录，群 ID 与标题都对得上
> - 想验去重：1 小时内对同一帖再触发一次，群里不再收到、状态里也不新增 `失败` 行
>   （只有日志出现 `qq-bot: 跳过 topic.created（duplicate）`）

## 9. 收尾

- 验收期间临时开过的「详细日志」记得关掉（「测试」组）。
- 排查时开过「暂停推送」的话，确认已经关回去，否则线上一条都推不出去。
- 需要重跑制品摘要：`./scripts/prepare-package.sh`；它同时会跑
  `extension validate` / `brand check` / `test`。
- 摘要为什么会在 dev 与 release 之间不一样：看 `NOTES.md` §11，别再当 bug 查一遍。
- 徽标显示「连接异常」时先读它下面那句原因：带「取凭证接口…」的是凭据/解析问题（凭据不对、
  接口返回的形状变了）；写「连不上 QQ 接口」的是网络/代理问题（连不到 `api.bot.qq.com`、代理没通）。
  这两类在 0.4.1 起分开报，别混着查。
